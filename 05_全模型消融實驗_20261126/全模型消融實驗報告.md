# 全模型消融實驗：MTP on/off × 效能 × 功耗（2026-11-26）

> 目的：用**同一套 for_jetson 導航測試**，公平比較電腦裡所有 llama.cpp 模型，唯一變因 = MTP 開關。
> 統一條件：llama.cpp build-sm87、**不用 Edge-LLM**、`-c 4096 -t 6 -ngl 99 -fa on`、KV q8_0、eval_jetson.py `/completion`。
> 硬體：Jetson Orin NX 16GB / MAXN_SUPER。

## 二、MTP 消融（同模型 off vs on）

| 模型 | decode off | decode on | 提升 | 正確率變化 | RAM 增加 |
|---|---|---|---|---|---|
| Gemma4 Q4_K_M | 13.3 | 18.2 | **+37%** | 不變 | +0.3 GB |
| Ornith v6 | 9.9 | 18.9 | **+91%** | 不變 | +1.9 GB |

**結論：MTP 對 decode 有 +37～91% 提升，且不影響正確率**（投機解碼 lossless）。
代價：RAM 增加 0.3–1.9 GB（Gemma 的 draft 是獨立 57MB；Ornith 的 MTP 內建但執行時多配置）。

## 四、公平性聲明（重要）

1. **框架/精度/測試統一**：全部 llama.cpp、Q4_K_M 為主、同 prompt、同 context/threads。
2. **模型訓練程度不同**：Ornith v6 有 **LoRA 微調**（訓練紅利），Gemma/Qwen 未 fine-tune → 正確率差距主因是「訓練」非「架構」。
3. **decode 用強制 64 token**：避免短輸出（導航只 7 token）導致 decode 測不到，公平隔離純速度。
4. **功耗為 VDD_IN 電軌**：非整板總功耗，僅供相對比較。
5. **不使用 Edge-LLM**（依需求），純 llama.cpp 公平比。

---

## 五、結論

1. **MTP 是有效加速**：decode +37～91%，正確率不變，功耗不增。
2. **正確率**：Ornith v6（LoRA）最強 100%/93%；Gemma4 未訓練 82%/70%。
3. **速度**：Gemma4 與 Ornith+MTP 的 decode 相當（~18）；Gemma4 prefill 較快。
4. **記憶體**：Qwen3.5-4B 最省（9.6GB）；Ornith+MTP 最吃（12.3GB）。
5. **能效**：MTP 讓同功耗產更多 token → 每 Joule 產出更高。

## 七、重現方式

```bash
# 1) 啟動 llama.cpp server（範例：Gemma4 Q4_K_M + MTP）
llama-server -m <Q4_K_M.gguf> -md <mtp-Q4_0.gguf> \
  --spec-type draft-mtp --spec-draft-n-max 6 \
  -ngl 99 -fa on -c 4096 -b 512 -ub 256 -t 6 \
  -ctk q8_0 -ctv q8_0 --host 127.0.0.1 --port 8080

# 2) 跑正確率（124 + 30 題）
python3 eval_jetson.py --port 8080 --testset datasets/nav_testset.jsonl \
  --tag my_test --out my_test.json
python3 eval_jetson.py --port 8080 --testset datasets/nav_holdout_v1.jsonl \
  --tag my_hold --out my_hold.json

# 3) 跑 6 配置消融 + 公平 decode
#    先修改 run_ablation.py / decode_test.py 內的路徑（LLAMA、模型、PY、EVAL、DATA）
python3 run_ablation.py
python3 decode_test.py
```

> 腳本內路徑是作者機器（`/home/jetson/...`）的設定，換機器只需改 `LLAMA`、模型路徑、`PY`、`EVAL`、`DATA`。
> 測試集與評估腳本已一併附上，`eval_jetson.py` 的 prompt 規則與 05 實驗完全一致。
