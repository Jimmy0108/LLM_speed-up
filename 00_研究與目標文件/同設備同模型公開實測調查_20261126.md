> 方法：3 個研究子 agent 分頭查 GitHub / CSDN / 學術論文，交叉驗證。
> 問題：有沒有人用「Jetson Orin NX 16GB + Gemma 4 E4B + MTP」做到 50 tok/s？

---

## 一、一句話結論

**沒有人公布「完全同條件（Orin NX + E4B + Q4_K_M + llama.cpp 內建 MTP）且 50+ tok/s」的數據。**
我們目前的 **40.5 tok/s** 已是同條件公開值的約 **2 倍**，屬領先水準。

## 三、little-gemma 的 57.8 是怎麼來的（不可直接對標）

- 專案：https://github.com/cortexist/little-gemma （作者 = NVIDIA 論壇 engineering66）
- **不是 llama.cpp**，是從零手寫的 C/CUDA 引擎（~5000 行，Karpathy llama2.c 精神）
- MTP 是自幹 `mtp.c` + 自研 2-row verify kernel
- 用 **QAT q4_0**（非 Q4_K_M）
- 57.8 = **counting（高度可預測）任務 + block-4** 的峰值；一般混合只有 38.1
- 我們的 40.5（Q4_K_M + llama.cpp MTP）已與它的「一般混合 38.1」同級

---

## 四、MTP 的關鍵特性（文獻+實測）

1. **MTP 本質是「用算力換頻寬」**，在 batch=1 邊緣 decode 是甜區（Staged Speculative Decoding, arXiv:2308.04623）。
2. **接受率依內容差 3–4 倍**：code 72% vs prose 19%（jetson-llamacpp-benchmarks 實測）。
   - prose 開 MTP 反而 **-38%**（31→19.2）；code **+37%**（31→42.7）。
   - → **Adaptive Draft Length 是必要條件，不是加分項**。
3. **Gemma 4 官方 Selected Vocabulary**：`d×262,000 → d×4096`（clustered top-k），接受率幾乎不變（Gemma 4 Technical Report, arXiv:2607.02770）→ 背書我們的方向。
4. **記憶體頻寬是瓶頸**：Orin NX 102.4 GB/s，推估 40→50–60（+30–40%）在射程內。

## 六、要達 50+ 的最現實路線（文獻共識）

1. **Adaptive Draft Length**（最高 CP 值、最安全）：依近期接受率動態調 n-max。
2. **Selected Vocabulary Head**：與 Gemma 4 官方一致（clustered top-k / SpecVocab 2048 候選）。
3. **Small GEMM specialization**：加速驗證階段小 batch GEMM（tinygemm/MARLIN 思路）。
4. 或換 **QAT q4_0 + 高接受率任務（code/counting）** — 但偏離我們 Q4_K_M 條件。
