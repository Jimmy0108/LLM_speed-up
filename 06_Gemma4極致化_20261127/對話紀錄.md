## 二、TensorRT-Edge-LLM 評估

### 2.1 為什麼要換？—— 效能預期

根据 NVIDIA 官方 benchmark（Orin NX 16GB, JetPack 7.2）：

| 模型 | 框架 | Prefill (t/s) | Decode (t/s) | 記憶體 |
|---|---|---|---|---|
| Qwen3.5-4B | **Edge-LLM INT4 AWQ** | **~703** | **~26.2** | 6.1 GB |
| Qwen3.5-4B | llama.cpp Q4_K_M | 650 | 16.2 | ~3.8 GB |
| Qwen3-8B | Edge-LLM INT4 AWQ | ~601 | ~18.6 | 8.2 GB |
| Ornith-1.5-9B | Edge-LLM INT4 AWQ (估計) | ~450–550 | ~14–17 | ~9–10 GB |
| Ornith-1.5-9B | llama.cpp Q4_K_M | 377 | 13.3 | ~6.5 GB |

**潛在提升：**

- Prefill 速度：約 **1.2–1.9x**（視模型大小而定）
- Decode 速度：約 **1.2–1.6x**（INT4 AWQ + 優化 kernel）
- **真實場景（含 cache）**：預估從 13.3 t/s 提升到 **16–20 t/s**

> - 可能需要手動從 HuggingFace 下載官方 Qwen3.5-9B 並轉換

### 2.4 安裝與建置流程（摘要）

```bash
# 1. 安裝依賴
sudo apt install -y cmake build-essential git \
    cuda-toolkit-13-2 libnvinfer-headers-dev libnvinfer-dev libnvonnxparsers-dev

# 2. 取得 Edge-LLM SDK
git clone https://github.com/NVIDIA/TensorRT-Edge-LLM.git
cd TensorRT-Edge-LLM

# 3. 安裝 Python 套件（可選，用於 checkpoint 轉換）
pip install tensorrt-edgellm

# 4. 下載並轉換模型
# 範例：Qwen3.5-4B
tensorrt-edgellm-export Qwen/Qwen3.5-4B-Instruct-2507 \
    --precision int4_awq --output-dir ./qwen3.5-4b-int4

# 5. 在裝置上建置 engine（Orin 必須在 device 上 build）
./build/examples/llm/llm_build \
    --engineDir ./qwen3.5-4b-int4/engine \
    --maxInputLen 8192 \
    --maxKVCacheCapacity 10240 \
    --externalize-weights int4_ffn

# 6. 啟動 OpenAI-compatible server
edgellm serve Qwen/Qwen3.5-4B \
    --max-input-len 8192 \
    --max-kv-cache-capacity 10240
```

### 2.5 風險與限制

| 項目 | 風險等級 | 說明 |
|---|---|---|
| 16GB 記憶體 build engine | 🟡 中 | 9B 模型 INT4 engine build 可能需要 `--externalize-weights int4_ffn`，否則可能 OOM |
| Ornith MTP head 相容性 | 🟡 中 | Edge-LLM 支援 Qwen3.5 但非 Ornith 官方 checkpoint；MTP 可能需要手動設定 |
| Web UI 遺失 | 🟡 中 | Edge-LLM 只有 OpenAI-compatible API，**沒有 llama-server 內建的 Web UI**；需另外做前端 |
| 學習曲線 | 🟡 中 | 新框架、新 API、新建置流程；systemd/監控腳本需重寫 |
| 量化品質 | 🟢 低 | INT4 AWQ 與 Q4_K_M 品質相近，但仍建議重跑 66 題邏輯測試驗證 |
| 功耗模式 | 🟢 低 | 目前 40W 模式；可隨時切換 MAXN 獲得 10–20% 效能提升 |

## 完整的現況分析

### 已驗證可用的成果

| 測試 | 框架 | 精度 | 模型大小 | TTFT | Prefill | Decode | 記憶體 |
|---|---|---|---|---|---|---|---|
| Qwen3.5-4B | Edge-LLM | FP16 | 8.8 GB | **151ms** | **840 t/s** | 11.4 t/s | ~12.8 GB |
| Qwen3.5-4B | llama.cpp | Q4_K_M | 2.9 GB | ~300ms | 655 t/s | **15.8 t/s** | ~8.5 GB |
| Ornith-1.5-9B | llama.cpp | Q4_K_M | 5.8 GB | ~300ms | 360 t/s | **12.1 t/s** | ~10 GB |

### 核心問題：9B 模型在 Edge-LLM 上的記憶體 constraint

```
Orin NX 16GB 可用記憶體：~15.5 GB

FP16 9B 模型：   ~17 GB   → ❌ 放不下
INT4 AWQ 9B：    ~5-6 GB  → ✅ 可行，但需要量化流程
INT8 9B：        ~9 GB    → ✅ 可行，但 Edge-LLM 的 INT8 是 SmoothQuant
```

### Edge-LLM 跑 9B 的唯一可行路線：INT4 AWQ

需要三步：
1. **Quantize**: `trtedge quantize llm --quantization int4_awq`（需要 PyTorch + nvidia-modelopt + calibration dataset + 大量 RAM 做 forward pass）
2. **Export**: `trtedge export` → ONNX
3. **Build**: `llm_build` → TensorRT engine

**但 Quantize 這步本身就會遇到 RAM 問題** — 做 AWQ calibration 需要跑 forward pass，9B FP16 模型 + calibration data 在 16GB 上可能 OOM。

## assistant

MTP 本質上是**投機解碼**：用一個小 draft head 先猜好幾個 token，然後一次驗證。如果猜對就跳過多次 decode。

## 為什麼能快 30-50%

### 沒有 MTP（正常 decode）

```
每個 token 要跑一次完整 forward pass：
token 1 → GPU forward（~63ms）→ 輸出
token 2 → GPU forward（~63ms）→ 輸出
token 3 → GPU forward（~63ms）→ 輸出
...
```

15.8 t/s = 每 token 約 63ms，全部花在 GPU forward。

### 有 MTP（投機解碼）

```
draft head 先猜 3 個 token（小模型，很快）：
  draft: "The" "quick" "brown"  ← 3 個猜測

然後一次 GPU forward 驗證 3 個：
  GPU forward（~63ms）→ "The"✅ "quick"✅ "brown"✅
  3 個 token 一次過！
```

**1 次 forward 產出 2-3 個 token**（接受率約 2-3 tokens/verify），所以：

| | 無 MTP | MTP（接受率 2.5） |
|---|---|---|
| 1 次 forward 產出 | 1 token | 2.5 tokens |
| 每 token 成本 | 63ms | 63ms ÷ 2.5 = 25ms |
| Decode 速度 | 15.8 t/s | **~40 t/s 理論值** |

### 實際會打折

- Draft head 猜錯的 token 要丟掉 → 接受率不是 100%
- Draft head 本身也要跑（佔用少量 GPU）
- 驗證 3 個 token 的 forward 比 1 個稍慢

所以實測通常 **+30-50%**（15.8 → 20-24 t/s），不是理論的 2.5x。

### 跟 Ornith 的 MTP 一樣道理

你的 Ornith-1.5-9B 在 llama.cpp 上已經用了 MTP n=3，從 8.9 → 11.6 t/s（+30%），就是這個機制。Gemma 4 的 MTP head 是 Google 另外訓練的 assistant checkpoint，原理相同。

## 滿了會怎樣 —— 靠 `--context-shift`

llama-server 有這個參數（查到的）：

```
--context-shift, --no-context-shift
    whether to use context shift on infinite text generation (default: 開啟)
```

| 情況 | 行為 |
|---|---|
| **預設（context-shift 開）** | 滿了 → **丟掉最舊的 token**，騰出空間繼續生成。有損截斷，**不是摘要** |
| `--no-context-shift` | 滿了 → **直接報錯/停止**，不再生成 |

所以：

- ❌ **不會自動「壓縮」**（llama.cpp 沒有內建摘要/summarization，不會把舊對話濃縮成重點）
- ✅ 預設會**自動截斷最舊的內容**（context shift），對話能一直聊下去，但**最早那段會被丟掉**
- 開頭的 system prompt 若不想被丟，可用 `--keep N` 保留前 N 個 token

你現在 4.09K/4.10K 快滿，接下來再聊，最舊的訊息會開始被丟掉（模型會「忘記」開頭講過的）。這就是為什麼長對話久了模型會前言不搭後語。

## 一、三個 S 級技術各自「改下去會怎樣」

### 1. Small GEMM Specialization（驗證效率）
- **做什麼**：MTP 驗證時是「小矩陣乘」，目前用通用 GEMM kernel，有 overhead。針對小尺寸寫專用 kernel。
- **改動範圍**：`ggml/src/ggml-cuda/` 新增/改 `.cu` 檔，**核心運算路徑**。
- **風險**：🔴 **中高**。改錯會產生**錯誤的 logits → 模型輸出亂掉或品質下降**，而且不一定 crash，可能默默變笨。
- **收益**：文件估 verification 加速 1.5–2x → decode 有机会到 47–55 t/s。
- **可逆性**：✅ 可逆（備份 build 目錄即可）。

### 2. Adaptive Draft Length（無效投機）
- **做什麼**：動態調整每次猜幾個 token（低接受率時少猜、高接受率時多猜），減少浪費的 draft 運算。
- **改動範圍**：`llama-speculative.cpp` 的排程邏輯，**非核心運算**，改的是「策略」。
- **風險**：🟡 **中低**。邏輯 bug 頂多讓速度變慢或接受率下降，**不會算錯**（最終答案仍由 target model 驗證把關）。

- ❌ **單串流 decode**（跟 llama.cpp 一樣受頻寬限制）

| 問題 | 影響 |
|---|---|

## 那 Edge-LLM + MTP 會怎樣？

- decode 還是被頻寬卡住 → **還是 ~40，不會到 50+**
- TTFT 可能比 llama.cpp 快一點（154ms）
- 但 RAM 15GB + MTP draft → **可能直接 OOM**（你只剩 1GB 空間）

## 結論

| 你要的 | Edge-LLM 幫得上嗎 |
|---|---|
| decode 更快（>40） | ❌ 物理不可能，跟 llama.cpp 一樣 |
