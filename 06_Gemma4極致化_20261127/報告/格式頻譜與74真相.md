# 格式頻譜與「74」真相 — 為什麼 JSON 快、自由長文只有 27

> 日期：2026-11-27
> 模型：Gemma 4 E4B Q4_K_M + MTP Q4_0（不換、不下載）
> 引擎：llama.cpp 2d8a3250（SM87, FA=ON, CUDA graphs）
> 方法：n-max8、thinking OFF、temperature 0、max_tokens 128、cache_prompt False
> 樣本：每類 5 題 × 3 次 = 15；canonical JSON 另做 10 次冷啟動 + 30 次同題

## 0. 結論先講

1. **加速 100% 來自投機解碼的接受率**。同一顆 GPU、同一組 flag，無 MTP 就是 **11.9 t/s**；有 MTP 才變成 27（自由）或 64（JSON）。
2. **格式是最大變因**：JSON 63–66、code 27、table 23、prose 20（n-max8）。
3. **自由長文最佳 n-max3 = 27.0 t/s，構不到 30**。不是設定沒調對，是接受率上限（0.375，需 0.454）。
4. **74.4 是單次離群值**。canonical 短 JSON 穩定 **63–66 t/s**（10/10，accept 0.750）；74 不可重現。
5. **「50+ 不可達」要修正**：自由長文不可達；**結構化 JSON 可達且超過**（63–66）。

## 1. 格式頻譜（n-max8, thinking OFF, 128 tok）

| 格式 | 接受率 | decode 中位 | E2E 中位 | 產出 tokens | 備註 |
|---|---:|---:|---:|---:|---|
| **JSON（canonical 短題）** | **0.750** | **63–66** | **1.4–1.5 s** | 78 | 10/10 穩定 |
| JSON（6 項 × 3 欄位） | 0.539 | 48.7 | 2.9 s | 128 | 內容較長、後段較難猜 |
| JSON（加隨機後綴） | 0.550 | 50.0 | 1.9 s | 82 | 輸出被擾動 |

**只有 JSON 出現跳躍式提升**。表格/列點看起來「有結構」，但大部分 token 仍是自由文字，所以只比散文好一點。

## 3. 為什麼（step economics）

投機解碼的 decode 可以寫成：

```
decode = (每步產出 tokens) / (每步耗時)
       = (1 + accept × n) / t_step
```

| 配置 | n | accept | tokens/step | decode | t_step |
|---|---:|---:|---:|---:|---:|
| 無 MTP | 0 | 0 | 1.00 | 11.9 | 84 ms |
| 自由 n3 | 3 | 0.375 | 2.12 | 27.0 | 79 ms |
| 自由 n4 | 4 | 0.255 | 2.02 | 24.3 | 83 ms |
| 自由 n6 | 6 | 0.204 | 2.22 | 25.4 | 88 ms |
| 自由 n8 | 8 | 0.142 | 2.14 | 21.2 | 101 ms |
| **JSON canonical n8** | 8 | **0.750** | **7.00** | **64.5** | 109 ms |
| JSON 6-item n8 | 8 | 0.539 | 5.31 | 48.7 | 109 ms |
| Code n8 | 8 | 0.231 | 2.85 | 27.4 | 104 ms |
| Table n8 | 8 | 0.197 | 2.58 | 23.3 | 111 ms |

兩個關鍵：

1. **驗證 9 個 token 只比生成 1 個 token 貴 30%**（109 vs 84 ms）——因為 GPU 是記憶體頻寬綁定，權重讀一次可以驗多個 draft。這就是投機解碼能加速的原因。
2. **自由長文的 tokens/step 卡在 ~2.1–2.2**；JSON 可以到 5.4–7.0。差距完全來自「每步被接受幾個 draft」。

## 4. 「74」的真相

### 冷啟動 10 次（完全相同的 canonical prompt）

```
#1  62.3 t/s  accept 0.750  pred_n 78  E2E 1746ms  md5 0c1b2964
#2  64.4 t/s  accept 0.750  pred_n 78  E2E 1464ms  md5 0c1b2964
...
#10 62.6 t/s  accept 0.750  pred_n 78  E2E 1511ms  md5 0c1b2964
```

→ 10/10 同一個輸出、同一個接受率，**穩定 61–64**（後續再測 62–66）。

### 加隨機後綴（`[u-123]`）×10

```
#1  52.3 t/s  accept 0.589  pred_n 81  md5 6aaf9cd9
#2  50.3 t/s  accept 0.550  pred_n 82  md5 1b322bee
...
#10 49.4 t/s  accept 0.550  pred_n 82  md5 1b322bee
```

→ 後綴讓模型產出**不同內容**（md5 變了），接受率掉到 0.55，decode 49–52。

### 74.4 是哪來的？

- 那是**單次請求**，accept 0.750、pred_n 78，跟 canonical 完全一樣，但 decode 75.4。
- 負載時 GPU 已固定在最高 **1173 MHz**（取樣 73 點，72 點在 max），所以不是時脈差異。
- 穩定帶是 **63–66**；74.4 高出約 15%，屬於單次量測離群（first-batch/排程瞬時），**不可重現、不應寫成規格**。

### 先前「57.3」的定位

- 那是 5 個短 JSON 題 ×3、**每題都加隨機後綴**的中位，接受率 0.60。
- 與這輪「加後綴 50、canonical 64」一致：**57 是中間值，不是上限**。

## 5. 加速槓桿總表（這輪所有操作）

| 槓桿 | 實測效果 | 機制 |
|---|---|---|
| **MTP draft** | 11.9 → 27（自由）/ 64（JSON） | 每步多驗 n 個 draft，權重只讀一次 |
| **n-max** | 自由 n3、JSON n8 | 接受率 × n vs 驗證成本 |
| **輸出格式** | JSON 比散文快 2.4×（n8） | 語法/key 重複 → 高接受率 |
| **prompt canonicality** | accept 0.75 vs 0.55 | 無隨機後綴 → 輸出更定型 |
| **thinking ON** | 40 t/s（accept 0.48） | 推理文本公式化、可預測 |
| **短答配方** | E2E 545–635 ms | lite prompt + n3 + ctx2048/b1024/t4 |
| **引擎 flag** | FA on 必須、q8_0 KV、t2、CUDA graphs | 頻寬/延遲 |
| **Adaptive draft（C1）** | lossless，但贏不了最佳固定 n | 已知負載無增益 |

## 6. 實用配方

### 要 63–66 t/s（結構化短 JSON）
```
--spec-draft-n-max 8 ... --reasoning off
prompt：用 JSON 陣列列出三個常見水果，每個含 name 與 color 欄位。
（不要加無意義的尾隨 token）
```
→ decode 63–66、E2E 1.4–1.5 s（78 tok）

### 要 48–52 t/s（長 JSON）
```
--spec-draft-n-max 8
prompt：用 JSON 陣列列出 6 個…，每個含 3 個欄位。
```
→ decode 48.7、E2E 2.9 s（128 tok）

### 自由長文（無格式要求）
```
--spec-draft-n-max 3
```
→ **27.0 t/s 上限**、E2E 5.5 s（128 tok）

### 要 40 t/s 的推理型長答
```
--spec-draft-n-max 6 + thinking ON
```
→ 39.9 中位、峰值 47.5

### 短答
```
lite rules + n-max3 + ctx2048 + b1024 + t4
```
→ E2E 545–635 ms、EM 88.7%

## 7. 注意事項

- 這是**工作負載相關**的加速，不是全域引擎加速：同一組 flag，格式一換就從 64 掉到 20。
- 74 不是規格；對外請用 **63–66（canonical 短 JSON）** 或 **48–52（一般 JSON）**。
- benchmark harness 加隨機後綴是為了避快取，但會改變輸出內容與接受率；比較格式時應固定 canonical prompt。
- JSON 輸出已驗證合法（`json.loads` 通過）；投機解碼 lossless（greedy byte-identical）。
