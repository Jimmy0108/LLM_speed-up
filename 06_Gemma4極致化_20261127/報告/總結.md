# 總結 — Gemma 4 E4B 極致化實驗（2026-11-27）

> 模型：Gemma 4 E4B Q4_K_M + MTP draft Q4_0（固定不換）
> 硬體：Jetson Orin NX 16GB / MAXN_SUPER / L4T R39.2.2 / llama.cpp 2d8a3250

## 一、最終配方與數據

### 短輸出（E2E 極快）
```
llama-server -m <Q4_K_M> -md <mtp-Q4_0.gguf> --spec-type draft-mtp \
  --spec-draft-n-max 3 -ngl 99 -fa on -c 2048 -b 1024 -ub 256 -t 4 \
  -ctk q8_0 -ctv q8_0 -np 1
+ prompt 用 lite rules（62 token）
```
| 指標 | 原本 | 極致 | 提升 |
|---|---:|---:|---:|
| E2E（124 題中位） | 731 ms | **536 ms** | **−27%** |
| E2E（100 次 p95） | — | **520 ms** | — |
| EM | 0.8226 | **0.8952** | +8.8% |
| F1 | 0.9447 | **0.9742** | +3.1% |

> `-np 1` 是 G 系列新增：多槽會把 2048 ctx 切成 512/slot，prefill 357→248ms、E2E −17%。代價是不能同時服務多請求（導航為序列式，可接受）。

### 長輸出（decode 極快）
```
--spec-draft-n-max 6 -t 2 -c 4096（thinking ON）
```
| 指標 | 值 |
|---|---:|
| decode（思考內容） | **40.8 t/s** |
| decode（雙路徑長答） | **39.9 中位（峰值 47.5）** |
| **decode（結構化 JSON, n8）** | **63–66 t/s（canonical 短題；一般 JSON 48–52）** |
| 接受率 | 48%（思考）/ 75%（canonical JSON） |

## 二、六大發現

1. **lite 規則是短答關鍵**：prompt 187→62 token，E2E 751→635ms，且 EM 反升到 88.7%（full rules 反而干擾）。
2. **MTP 有開就比沒開快**：短答 641 vs 761ms；n-max3 最佳。
3. **ctx2048+b1024+t4** 再快 5%（609ms）。
4. **thinking ON 讓 decode 40.8**（vs OFF 26.5），思考內容可預測、接受率 48%。
5. **n-max 對思考內容不敏感**（4/6/8 都 40–41）→ 已近頻寬極限。
6. **GPU 利用率 97%、功耗 20.6W、70°C 無降頻** → 硬體已吃滿，改 kernel 空間有限。

## 三、瓶頸分析（IO/運算）

| 瓶頸 | 證據 | 對策 |
|---|---|---|
| **prefill（短答）** | lite 62 tok 仍佔 E2E 大半 | 已用 lite 降 prompt |
| **SYNC_OVERHEAD（短答 MTP）** | 短答 draft 開銷占比高 | n-max3 + 短輸出 |
| **頻寬（長答 decode）** | 40.8 vs 51 理論，gap 21% | 提高接受率（JSON 63–66）；自由長文受 acceptance 限制 |
| **COMPUTE_BOUND（長 prompt）** | in512 prefill 掉到 140 t/s | 長 prompt 無解（compute） |

## 四、目標達成度

| 目標 | 現況 | 達成 |
|---|---|---|
| 短答 E2E ≤300ms | 545–635ms | ⚠️ 未達（差 245ms，卡在 prefill）|
| 長答 decode ≥50 | 自由 27.0 / 思考 39.9 / **JSON 63–66** | ✅ 結構化達標；自由未達 |
| 正確率不降 | 88.7%（升） | ✅ |
| 穩定 | 0 失敗、無降頻 | ✅ |

## 五、要達 300ms / 50t/s 的下一步
- **短答 300ms**：需砍 prefill（更短 prompt 或 cache 重用），或接受 545ms（已比原 731 快）。
- **長答 50t/s**：自由長文不可達（n3 上限 27.0）；**結構化 JSON 已達 63–66**。C1 adaptive 對已知負載無增益。

## 六、研究級 C1（Adaptive Draft）結論

- 實作 `--spec-adaptive`（rolling EWMA 調 n_max），**lossless**（greedy 輸出 byte-identical）。
- **思考 decode 結構天花板 = 40–42 t/s（fixed n-max6，中位 39.9、峰值 47.5）**；adaptive 38–41 打不贏已調最佳固定值。
- n>6 變慢、KV q4_0 變慢、FA off 壞（sm_87 bug）、2-row verify 不需（mmq-few 已 optimal）。
- **自由長文 50 t/s 不可達**（n3 上限 27.0，GPU 97% mem-bound）；**結構化 JSON 可達 63–66**（格式相關，非全域加速）。
- adaptive 的價值：未知/混合負載 +5–15%（避免固定 n 懲罰），已知最佳固定值 ~0%。

## 七、格式頻譜（為什麼 JSON 快、自由慢）

| 格式（n-max8） | 接受率 | decode | E2E(128tok) |
|---|---:|---:|---:|
| **JSON canonical 短題** | **0.750** | **63–66 t/s** | 1.4–1.5 s |
| JSON 6 項 / 128 tok | 0.539 | 48.7 | 2.9 s |
| Code | 0.231 | 27.4 | 4.9 s |
| Markdown 表格 | 0.197 | 23.3 | 5.8 s |
| 自由散文 | 0.142 | 19.7 | 6.8 s |

- **無 MTP 基線 11.9 t/s** → 加速全部來自投機接受率，不是 GPU 變快。
- 自由長文最佳 **n3 = 27.0**；要 30 t/s 需 accept 0.454（實際 0.375），**不可達**。
- **74.4 是單次離群值**；canonical 短 JSON 穩定 **63–66**（10/10、accept 0.75）。
- 詳見 `報告/格式頻譜與74真相.md`。

## 九、算子融合與計算圖（G 系列）

| 項目 | 結果 |
|---|---|
| GPU kernel 組成（nsys） | 量化 matmul ≈ 80%；glue/norm/GLU 合計 <6% |
| Fusion ON/OFF | 散文 **+7.3%**、prefill **+3.8%**、JSON +1.1% |
| `GGML_CUDA_GRAPH_OPT` | **無效** |
| CUDA Graph 本體 | **decode +11–12%**（關掉即掉） |
| MMQ q4/q8 精度 | 無效 |
| GEGLU 未融合 | batch 8 走 `mul_mat_q_few`，上游刻意排除；上限 ≤1.5%，不做 |
| Prompt prefix cache | Gemma4 KV sharing → `cache_reuse` 停用；只有整段相同 prompt 有效（prefill −45%） |
| Roofline | 每步實際串流 3.02 GB；自由長文 48 GB/s ≈ 實測屋頂 57–66 GB/s 的 73–84% |
| 100 次穩定性 | E2E 中位 505ms、p95 520ms、輸出 100/100 一致、20.4–20.7W、≤73°C |

> 結論：融合沒有大 headroom（Amdahl 上限 ~1.02×）；真正有效的是 MTP 接受率、CUDA Graph、單槽 prefill。詳見 `報告/算子融合與計算圖最佳化_G系列.md`。
